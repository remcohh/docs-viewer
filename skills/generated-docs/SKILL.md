---
name: generated-docs
description: Write, regenerate or check AI-generated docs and diagrams in a project's docs/ folder. Use when drawing a diagram or writing an explanatory doc from the code, when asked to regenerate or refresh one, or to find which ones are stale.
---

An AI-generated doc carries its own **recipe** in a header: the prompt that produced it, the
sources it was read from, and the commit it was generated at. The recipe is the source of truth;
the body is its output. Regenerating means re-running the recipe against today's code.

## The header

The doc's first comment block: `%%` lines in a `.mmd` file, one `<!-- -->` comment at the very top
of a `.md` file (both stay invisible in the docs viewer).

```
%% AI-GENERATED: regenerate with the generated-docs skill rather than editing by hand.
%% generated-at: <short commit SHA of HEAD when generated>
%% sources: <project-relative paths, space-separated: files or directories>
%% prompt:
%%   <what the doc must show, for whom, its scope and what it leaves out>
```

- **sources** are git pathspecs relative to the project root: the folder that contains `docs/`
  (in a monorepo, the app's folder, not the repo root). List every file or directory the body
  describes, and nothing it merely mentions in passing: a source that changes marks the doc stale.
- **prompt** states intent and scope, not wording: the audience, what must be shown, the diagram
  type, what is out of scope. Write it so a fresh agent with only the prompt and the sources
  produces an equivalent doc.
- Docs produced by a script (`GENERATED by scripts/...`) are a different kind: rerun their script.

## Checking for stale docs

`docs-check` lists every generated doc and whether its sources changed since `generated-at`;
it exits 1 when any doc is stale. Projects usually wire it up as a `docs:check` script; otherwise
run it from the project root:

```
npx -y -p github:remcohh/docs-viewer docs-check docs
```

## Writing a new generated doc

1. Read every source until each claim in the doc traces to code.
2. Write the body, then the header, with `generated-at` set to `git rev-parse --short HEAD`.
3. Put the user's request into the prompt, sharpened with the scope decisions you made along the
   way.

## Regenerating

1. Run `docs-check` to see which sources changed since `generated-at`.
2. Read the prompt, then read the sources as they are now. Treat the old body as a hint for layout
   only: every claim is re-verified against the code.
3. Rewrite the body to fulfil the prompt. Keep the header; update `generated-at` to the current
   short HEAD and `sources` if files moved, appeared or went away.
4. If the doc had been corrected by hand since its last generation (`git log <generated-at>.. --
   <doc>`), carry the correction into the prompt so the next run keeps it.
5. Done when `docs-check` shows a ✓ for the doc and the diagram renders in the docs viewer.

Tell the user which claims changed, so a reviewer can check the diff against the code.
